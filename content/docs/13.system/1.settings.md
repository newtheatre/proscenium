Settings is where every operational number the theatre works to is kept: booking windows,
caps, notice periods, warning cadences, fees. It is at **Manage, System, Settings**. The IT
Manager, the Manager and the Theatre Manager read it, and the IT Manager alone changes a value.
A change takes effect on the next page anybody opens, so a committee decision is a change made
here and never a release.

::callout{icon="i-lucide-info" color="info"}
**A key is a rule, not a record.** Each setting is one validated configuration key, headed by what
it decides, such as **Longest room booking**, with its name beneath, such as
`ROOM_MAX_BOOKING_HOURS`. It carries a description and the value it ships with.
The value it ships with is the one the Phase 0 workshops proposed; a key the workshops proposed
no value for ships unset and shows **Not set** until somebody fills it in. Lists of people (pass
products, the roll of Fellows) are records kept on their own screens, not settings.
::

## If something goes wrong

- **"That is not a valid value for KEY"**: the value is the wrong type or outside the key's
  range. The description says what the key expects.
- **"The final warning cannot come before the first one"**, **"A no-show has to be recorded
  before it can require pre-approval"**, **"The nags cannot start after they stop"**: a pair of
  keys would contradict each other. Change the other key first, or choose a value that keeps
  the order.
- **"A yearly boundary must fall in every year, and 29 February does not"**: choose another day.
- **"Treasurer must stay on this list: every role touching money, personal data or safety records
  needs a second factor"**: the roles that need a second factor can gain a role and never lose
  one of these. Put the named role back. Any role the committee added itself can come off.
- **"Type "KEY" or "N" to confirm this change."**: the confirmation did not match the setting's
  name or the previewed count. Read the preview again and type one of the two exactly.
- **"Retention cannot be armed until a dry-run digest has gone out to review"**: nothing has
  been reviewed yet. What would be closed is reported first; switch it on once that has been
  read.
- **"This setting has no prior value on the trail to revert to"**: the key's last change is a
  hashed one, or the trail carries no change for it. Type the value back in.
- **"Set up an authenticator app"**: the action needs a second factor on your account. The
  button takes you to your security settings; enrol, then try again.
- **"No setting in this group matches that."**: the search matched nothing on this tab. Clear
  it, or check another tab's count.

## Finding a setting

![Settings with the search field (1), one setting's card (2), its input (3) and its Save button (4)](/images/docs/system/settings.png)

1. **Search** matches the heading, the key's name and its description, so "tab cap" finds
   `BAR_TAB_CAP_PENCE` without you remembering the name. The tabs count their matches, and a
   search that empties the tab you are on moves you to the first tab that has one.
2. The tabs group the keys by the workshop that owns them: **Money and box office**, **Spaces
   and training**, **People and communications**. Each **setting** is headed by what it
   decides, with the key's name beneath and a description, and beneath the input what it ships
   as and who last changed it, or **Never changed**.
3. **The input** matches the kind of value: a switch for yes or no, a pounds field for a money
   key (stored as pence), a calendar for a day of the year, a person search for a list of
   people, a role menu for a list of roles, a number field with its unit beside it (minutes,
   hours, days, working days, weeks, months, years or %), a tag field for any other list, or a
   text field for anything else.
4. **Save** writes the value. **Saved** appears beside the button when it has.

At the foot of each tab, **Technical limits** is folded shut. These say how much one scheduled
run may do at once, such as how many held seats one release run lets go: a backlog after an
outage clears over several runs rather than one huge batch. Nobody meets one as a rule.
Press **Technical limits** to open them; a search opens them too.

Four badges can sit on a card:

- **Wide blast radius**: saving this key asks for a preview and a typed confirmation, below.
- **Nothing enforces this**: the committee records the rule here and it is quoted wherever it is
  published, but changing it changes no refusal. A policy page quoting the key marks it the same
  way.
- **Not built**: a switch for a feature that has not been built, such as discount codes. The
  switch shows where it stands and cannot be moved: nothing would read it. The badge carries the
  number of the piece of work that builds the feature, and pressing it opens that work's page.
- **Not set**: the key has no shipped value and nobody has given it one. The feature that needs
  it is blocked rather than guessing.

## Reading without changing

The Manager and the Theatre Manager read the settings and change none. For them each card
shows its value in words, such as **15 minutes**, **£20.00**, **On** or a list of role titles,
with no input, no **Save**, no **Revert** and no **Sync now**.

## Changing a value

1. Find the setting and change its input.
2. Press **Save**.
3. Read the line beneath the input: it now names you and today's date.

A value is checked before it is stored. The key's own schema refuses the wrong type or range,
and a few keys are checked against each other, so the final training warning cannot come before
the first one and a no-show cannot require pre-approval before it is recorded at all. A yearly
boundary written as a month and a day must exist in every year, and 29 February is refused
for that reason. A refused value is never stored and the refusal names the rule.

Money is entered in pounds, to the penny, and stored in pence. A key that holds text keeps
exactly what you typed, so a value is never turned into a number or a yes or no behind your back.

## Choosing a day of the year

`YEAR_START`, `YEAR_END` and `ACADEMIC_YEAR_BOUNDARY` are days that come round every year, so
they have no year of their own. Each shows as a day and a month, such as **1 August**. Press it
and a calendar opens: move between months with the arrows, press the day, then press **Save**.
The calendar shows no year and no weekday names: the day falls on a different weekday each
year. It never offers 29 February, which is not in every year.

## Confirming a wide blast radius change

Four settings cannot be saved on a press: refund policy, retention arming, the roles that
need a second factor, and the first night that closes itself. Which settings these are is not itself a setting: it is kept with the
screens, and changing it is a reviewed change like any other, never a save here.

1. Change the value and press **Save**. A confirmation opens instead of saving.
2. Read the preview: the live count and category of who the change reaches, for example the
   box office officers who could self-approve a refund without the setting, the accounts
   already due anonymisation the moment retention is armed, or the role holders who sign in with
   a password and have no authenticator app. For the first night that closes itself, the
   preview counts the performances from the night you typed onwards that have no night report
   and are already more than 24 hours past their show night: overnight, each one is frozen
   and its report emailed. Set a night too early and this count is the imported
   performances it would mail; for the right night it is usually none. A key with no preview
   written for it says so and asks for its name instead.
3. Type either the setting's own name or the previewed count, exactly, into the field. A
   checkbox is never offered.
4. Press **Save anyway**.

Retention arming has one more gate: it is refused until a dry-run digest has actually been sent
out for review, however the confirmation is typed.

## Reverting a change

**Revert** shows on any setting that has been changed from what it ships with. It writes back
the value the key stood at immediately before its last change, read from the audit trail. The
revert is itself an audited change, and it passes through the same checks a save does.

For most settings a revert is one press with nothing more to ask. The four wide blast radius
settings above are the exception: a revert writes a value just as a save does, so it could arm
retention, add a second-factor role or move the first self-closing night earlier. The preview
counts what the value being written back would reach. Pressing **Revert** on one of them opens the same preview
and asks for the same typed confirmation as a save, and the button reads **Revert anyway**.

A sensitive key cannot be reverted this way: its trail carries a fingerprint rather than the
value (next section). Type the value back in instead.

## Sensitive keys and the change hash

A key whose value could identify a person, such as the members authorised to hold a bar tab, is
marked sensitive. A key naming roles is not: a role identifies nobody, so the roles who receive
the end-of-night report are recorded as themselves. A change to a sensitive key is recorded in
the audit trail as the key, the fact that it changed, and a short hash of the value on each side,
never the value. The trail still says which setting moved, when and by whom, and
somebody can later prove which value it held by hashing a candidate; it never holds an address.
This is why a sensitive key cannot be quoted on a policy or documentation page, and CI refuses a
page that tries.

## Who may run up a bar tab

Two keys decide it, and a charge to a tab is checked against both at the moment it is made:

- `BAR_AUTHORISED_TAB_HOLDERS` names people. Each shows by name; **Add somebody** searches the
  accounts by name, address or student number, and the cross beside a name takes them off. Press
  **Save** once the list is right.
- `BAR_AUTHORISED_TAB_ROLES` names roles. Everybody holding one of them may charge to a tab for as
  long as their grant lasts: a grant ends at the committee year end on 31 July unless it says
  otherwise, and credit by role ends with it.

::callout{icon="i-lucide-triangle-alert" color="warning"}
**A role extends credit to everybody who holds it.** Naming a role lets every holder, including
anybody granted it later in the year, run up a tab to the cap without being named here. Name a
role only when the committee has agreed that everybody in it should have credit at the bar.
::

Both lists start empty, so nobody can charge to a tab until one of them names somebody. The
people are a sensitive key (below). The roles are not: a role names nobody, and the audit trail
records the roles themselves.

## The holiday list

`BANK_HOLIDAYS` is the list of days that do not count towards notice when somebody asks for a
room the theatre does not manage: weekends never count, and these dates do not either. Nobody
types it. Every Monday morning the England and Wales dates gov.uk publishes are copied in,
about two years ahead, and the card shows the list **read-only**: there is no box to edit and no
**Revert**, and a change sent any other way is refused.

The card says how far the list reaches, and turns red once it no longer reaches as far ahead as
requests are judged, naming the last date it covers. Beneath that it lists the dates from today
on and says when gov.uk last supplied them.

- **"Not yet copied from gov.uk"**: a new environment, still on the dates it shipped with. Press
  **Sync now**.
- **"The last copy ... failed: ..."** (red): gov.uk did not answer, answered with an error, or
  sent something that was not a list of dates. **The list already held stands**, untouched, and
  requests are counted against it as before. Press **Sync now** to try again; the reason is also
  on `/api/health`. If it is still failing six days later (the second weekly run), the IT Manager
  is emailed.
- **"It should have been copied again since"** (amber): more than eight days without a successful
  copy, and no failure recorded either, which means the weekly run itself did not happen.

A request judged against a date past the end of the list is still refused rather than guessed,
so a copy that keeps failing costs nothing until the list runs out, and the warnings above exist
so it never gets that far. Each copy is in the audit trail as **Bank holidays copied from the
government's list** (or **could not be copied**), with whoever pressed **Sync now**; a copy that
changes the list also writes **Setting changed** with nobody named: the dates are gov.uk's rather
than anybody's here.

## What happens next

Every save and every revert writes a **Setting changed** entry to the audit trail with the
value before and after (or a hash pair for a sensitive key), and the card names you as the last
editor. The new value is read by the next request that needs it: the write path enforces it,
and any policy or documentation page quoting the key shows the new figure the next time it is
opened, with no content edit. A wide blast radius change carries its typed confirmation into
the same entry.
