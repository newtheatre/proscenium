Everything the theatre holds is in one place, so everything stands or falls with it. Backups
is where the IT Manager proves, on a cadence, that it can be brought back: it is at **Manage,
System, Backups**, and the IT Manager alone reads it and records a drill on it. The page is
written for a successor running the drill cold, with the committee password manager, this page
and nobody to ask.

::callout{icon="i-lucide-info" color="info"}
**There are two backups, and neither is a copy you download.** Cloudflare D1 keeps a
point-in-time history of the production database (Time Travel) for thirty days, and every
migration takes a named restore point in it before touching anything. Separately, every Monday
at 05:00 a manifest is written to storage that stands apart from the data itself: a row count for
every table and the ledger's total in pence. The manifest is what the drill reconciles against.
It is deliberately not a second copy of the data: a copy of personal data that erasure could
never reach is not something to keep quietly.
::

## If something goes wrong

- **"A drill is overdue"** or **"No drill has ever passed"**: the interval has run out, or no
  drill has ever been recorded as passing. Run one.
- **"No cadence is configured, so this should not be flagged."**: how often a drill is due has
  never been set. Set it on Settings; until then nothing is flagged.
- **"Give the date as YYYY-MM-DD"**: the date field did not receive a full date.
- **"Say what the drill found"**: the notes field was opened and left empty. Either write the
  note or leave the field untouched.
- **"You do not have permission to do that"**: the screen and the form are the IT Manager's.

## Where a restore happens

Not on this screen. A restore and a drill are run by the IT Manager at the command line, step
by step, from the runbook in the repository; this screen records that a drill was run and what
it found. The screen says so, so nobody looks for a button that does not exist.

## What the screen shows

![Backups with the drill card (1), the search field (2), Record a drill (3) and the drill log (4)](/images/docs/system/backups.png)

1. **The drill card** says when a drill last passed. Once
   {{ BACKUP_DRILL_INTERVAL_DAYS }} have gone by since that date, or if no drill has ever
   passed, it flags **A drill is overdue** or **No drill has ever passed**. A drill that failed
   does not clear the flag: it is not evidence the backup restores, and the card says **The
   most recent attempt failed and is not counted**. A site just set up reads as overdue from the
   first day, which is what puts the first drill before the December break.
2. **Search** matches the operator's name or a note.
3. **Record a drill** opens the form, below.
4. **The drill log**, newest first: the date it ran, **Passed** or **Failed**, who ran it, the
   minutes it took to restore, which of **Row counts** and **Money totals** reconciled (or
   **Neither**), and the notes.

## Running the restore drill

The drill is run at the command line, and the steps are in the repository, in
`docs/operations.md` under **The restore drill**: export production, load the copy into a
scratch database, reconcile it against Monday's manifest, prove the restore on the scratch
database, record what you found here, and delete both copies. Nothing in it writes to
production, and nothing here starts it.

## Recording a drill

1. Press **Record a drill**.
2. Give the **Date run**.
3. Choose the **Outcome**, **Passed** or **Failed**. Nothing else is accepted, so a typo cannot
   invent a third state.
4. Enter the **Minutes to restore**.
5. Tick **Row counts matched production** and **Money totals matched production** as the
   reconciliation found. A pass with neither ticked is still recorded as you gave it, so be
   honest here rather than in the notes.
6. Add **Notes**: what did not reconcile, or anything a successor should know. Up to 500
   characters.
7. Press **Record the drill**.

## If the weekly export fails

A failed export does not vanish into a log. It writes a **Weekly export failed** entry to the
audit trail, attributed to **System**, with the error. Filter the trail by the governance
module to see it. The IT Manager can run the export again by hand; the runbook in the
repository says how.

## What happens next

Recording a drill writes the row to the drill log and a **Restore drill recorded** entry to the
audit trail in the same transaction, carrying the outcome and what reconciled. A pass resets
the overdue clock; a fail does not. Nothing in the log is edited: a mistake is corrected by recording
another drill with a note.
