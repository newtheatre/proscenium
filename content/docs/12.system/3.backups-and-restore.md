One application runs on one database, so that database is the whole blast radius. Backups is
where the IT Manager proves, on a cadence, that the backup restores: it is at **Manage, System,
Backups** and needs `backups.read` to see and `backups.write` to record, both held by
Administrators only. The page is written so that a successor can run the drill cold, with the
committee password manager and this page and nobody to ask.

::callout{icon="i-lucide-info" color="info"}
**There are two backups, and neither is a copy you download.** Cloudflare D1 keeps a
point-in-time history of the production database (Time Travel) for thirty days, and every
migration takes a named restore point in it before touching anything. Separately, every Monday
at 05:00 the system writes a manifest to storage independent of the database: a row count for
every table and the ledger's total in pence. The manifest is what the drill reconciles against.
It is deliberately not a second copy of the data, because a copy of personal data sitting
outside the erasure path is not something to keep quietly.
::

## What the screen shows

![Backups with the drill card (1), the search field (2), Record a drill (3) and the drill log (4)](/images/docs/system/backups.png)

1. **The drill card** says when a drill last passed. Once
   {{ BACKUP_DRILL_INTERVAL_DAYS }} have gone by since that date, or if no drill has ever
   passed, it flags **A drill is overdue** or **No drill has ever passed**. A drill that failed
   does not clear the flag: it is not evidence the backup restores, and the card says **The
   most recent attempt failed and is not counted**. A fresh deploy reads as overdue from the
   first day, which is what puts the first drill before the December break.
2. **Search** matches the operator's name or a note.
3. **Record a drill** opens the form, below.
4. **The drill log**, newest first: the date it ran, **Passed** or **Failed**, who ran it, the
   minutes it took to restore, which of **Row counts** and **Money totals** reconciled (or
   **Neither**), and the notes.

## Running the restore drill

You need the Cloudflare credentials from the committee password manager (the account id and an
API token that can read the production database and create, write and delete a D1 database of
its own), a checkout of the repository with its dependencies installed (`wrangler` is one of
them), and access to the Cloudflare dashboard for the bucket. Nothing in the drill writes to
production; write down the time you start.

::callout{icon="i-lucide-info" color="info"}
**Time Travel restores a database in place.** `wrangler d1 time-travel restore <database>
--bookmark=<bookmark>` takes a database back to one of its own bookmarks; there is no source
database to name, and `d1 export` has no bookmark option, so production's history cannot be
poured into a second database. The drill therefore copies production with an export, loads the
copy into a scratch database, and exercises Time Travel on that scratch database.
::

1. **Export production, read only.** From a checkout of the repository, with the credentials
   exported as `NUXT_HUB_CLOUDFLARE_ACCOUNT_ID` and `NUXT_HUB_CLOUDFLARE_API_TOKEN`, run
   `bunx wrangler d1 export unified --remote --output drill.sql`. Nothing is written to
   production by this, and the file it leaves is a copy of personal data: step 7 deletes it.
2. **Create the scratch database.** `bunx wrangler d1 create unified-drill`. Give it that name
   every time, so a stray database is recognisable as a drill leftover.
3. **Load the copy.** `bunx wrangler d1 execute unified-drill --remote --file=drill.sql`. Note
   the minute you started at step 1 and the minute this finishes: the difference is the
   **Minutes to restore** the form asks for.
4. **Reconcile.** The Monday manifest is in the `unified-blob` bucket, in the Cloudflare
   dashboard under R2, at `backups/<date>.json`; open the most recent one. It lists every table
   with its row count and `ledgerTotalPence`. Against `unified-drill`, run
   `bunx wrangler d1 execute unified-drill --remote --command="SELECT sum(total_pence) FROM
   ledger_entries"` and a row count per table, and compare both with the manifest. A difference
   of a few rows in tables that change daily is expected between Monday and the export; a table
   missing, a count out by hundreds, or a ledger total that disagrees is a finding.
5. **Exercise Time Travel, on the scratch database.** `bunx wrangler d1 time-travel info
   unified-drill` prints its own current bookmark; delete a row from it, then
   `bunx wrangler d1 time-travel restore unified-drill --bookmark=<bookmark>` and check the row
   is back. That is the mechanism itself proved, on a database nobody depends on. Never name
   `unified` in a restore command: restoring production is the disaster procedure, not the drill.
6. **Record the drill**, below, whether it passed or failed. A failure is the finding, not a reason to
   leave it out.
7. **Delete the scratch database and the export file.** `bunx wrangler d1 delete unified-drill`
   and remove `drill.sql` from the machine you ran it on. Both are full copies of personal data
   sitting outside the erasure path, so neither may be kept once the drill is recorded.

::callout{icon="i-lucide-alert-triangle" color="warning"}
**If a migration has gone wrong on production**, that is not a drill. The migration job's run
summary carries the exact restore command with its own bookmark; restore first, then fix the
migration and let the job run again. `docs/operations.md` in the repository is the runbook.
::

## Recording a drill

1. Press **Record a drill**.
2. Give the **Date run**.
3. Choose the **Outcome**, **Passed** or **Failed**. Nothing else is accepted, so a typo cannot
   invent a third state.
4. Enter the **Minutes to restore**.
5. Tick **Row counts matched production** and **Money totals matched production** as the
   reconciliation found. A pass with neither ticked is still recorded as you gave it, so be
   honest here rather than in the notes.
6. Add **Notes**: what did not reconcile, or anything a successor should know. Up to 500
   characters.
7. Press **Record the drill**.

## If the weekly export fails

A failed export does not vanish into a log. It writes a **Weekly export failed** entry to the
audit trail, attributed to **System**, with the error. Filter the trail by the governance
module to see it. The export can be run again by hand by an administrator with access to the
deployed worker, by posting to the `backup` scheduled task.

## If something goes wrong

- **"A drill is overdue"** or **"No drill has ever passed"**: the interval has run out, or no
  drill has ever been recorded as passing. Run one.
- **"No cadence is configured, so this should not be flagged."**: `BACKUP_DRILL_INTERVAL_DAYS`
  is unset. Set it in Settings; until then nothing is flagged.
- **"Give the date as YYYY-MM-DD"**: the date field did not receive a full date.
- **"Say what the drill found"**: the notes field was opened and left empty. Either write the
  note or leave the field untouched.
- **"You do not have permission to do that"**: the screen needs `backups.read` and the form
  `backups.write`, both Administrator permissions.

## What happens next

Recording a drill writes the row to the drill log and a **Restore drill recorded** entry to the
audit trail in the same transaction, carrying the outcome and what reconciled. A pass resets
the overdue clock; a fail does not. The log is append-only: a mistake is corrected by recording
another drill with a note.
