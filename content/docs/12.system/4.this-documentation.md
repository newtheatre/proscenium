This documentation is part of the application: it lives in the same repository as the code, is
reviewed in the same pull request as the behaviour it describes, and is served at `/docs` to
anybody signed in. There is no separate wiki to fall behind. This page is for the IT Manager,
or whoever else edits a page, and for anybody wondering why a page says what it says.

::callout{icon="i-lucide-info" color="info"}
**Drift is a defect.** When a screen changes and its page does not, that is a bug in the same
sense as a refusal that says the wrong thing, and it is fixed the same way: in a pull request,
by whoever changed the screen. The cautionary tale is the old rooms application, whose
published rules described a product the code did not contain.
::

## Reading the documentation

![The documentation with the sidebar (1), the search (2) and Report as out of date (3)](/images/docs/system/docs.png)

1. **The sidebar** is the whole tree, one section per area of the system, in the order the
   console shows them. On a phone it folds into the header menu.
2. **Search** reaches every page and every heading.
3. **Report as out of date** is on every page. Pressing it tells the IT Manager,
   naming the page and you, and writes an **Operator documentation flagged as out of date**
   entry to the audit trail. It needs no permission beyond being signed in, because the person
   on a shift is the one most likely to notice.

Beneath every title is the module the page belongs to and **Last updated** with a date and a
name. Where a page quotes a number the configuration owns, the number is the live setting,
read as the page renders, so a settings change is reflected here with no edit.

## Where the pages live

The pages are markdown files under `content/docs/` in the repository, one folder per section
and one file per screen:

```
content/docs/index.md                      /docs
content/docs/12.system/index.md            /docs/system
content/docs/12.system/1.settings.md       /docs/system/settings
content/docs/12.system/.navigation.yml     the section's title and icon in the sidebar
```

The number at the front of a folder or file name orders it in the sidebar and is dropped from
the address, as is `.md`; `index.md` is the section's own page. Links between pages use the
address form, `/docs/system/settings`. Every section folder carries a `.navigation.yml` naming
the section's title and icon.

## Front matter

Every page opens with the same block, in this order:

```
---
title: Settings
description: One sentence saying what the page is for, ending with a full stop.
module: Platform
updatedOn: 2026-09-15
updatedBy: Matt Adcock
navigation:
  icon: i-lucide-sliders-horizontal
---
```

There is no in-app editor, so `updatedOn` and `updatedBy` are set by hand by whoever edits the
page, in the same commit. `module` is the area of the backlog the screen belongs to.

## The shape of a page

Each page documents one screen, and only a screen that exists: a page file under
`app/pages/` and behaviour visible in its code. The backlog describes intent; the code is the
truth, and a promise the code does not yet keep is left out rather than written as coming.

- An opening paragraph: who the page is for, the permission or shift that reaches the screen,
  and where it is in the navigation.
- Tasks as numbered steps, with one annotated picture per screen after the step it
  illustrates, and a legend beneath saying what each numbered badge is.
- **If something goes wrong**, quoting each refusal in the screen's own wording.
- **What happens next**: what is recorded, who is told.
- **Related pages**.

A figure the configuration owns is never typed into the prose. It is written as a token, the
key's name inside a pair of double curly braces, and renders as the live value. A key marked sensitive,
because its value could name a person, cannot be quoted, and the build refuses a page that
tries. No em dashes anywhere; British English throughout.

## Pictures

Every picture is captured from a seeded development server, with numbered badges drawn over
the elements the legend names. A manifest per section under `scripts/docs-shots/` says, for
each picture, which page to open, as which seeded persona, at which width, and which elements
to number. The command is:

```
bun run docs:shots            # every picture
bun run docs:shots system     # one section, by name
```

The pictures are committed under `public/images/docs/`; the command is not part of the build.
Re-run it for a section whenever its screens change, and commit the new pictures with the page.

## Checks

`bun run check docs` fails when a page is missing its front matter, shows a picture that is not
in the repository, links to a page that does not exist, or a picture is shown by no page.
`bun run check content-tokens` fails on a token naming an unknown or sensitive key, and
`bun run check comments` fails on an em dash. All three run in CI on every pull request.

## The help link on each screen

Every console, member and show-night screen names its page, and the shell renders a **Help for
this screen** button that opens it. The screen names the page in its own file, and a unit test
fails when a screen names a page that does not exist, so a renamed page breaks the build rather
than the link.

## Making a change

1. Edit the page, or add one following the shape above.
2. Set `updatedOn` to today and `updatedBy` to your name.
3. If a screen changed, re-run the pictures for its section.
4. Run the three checks.
5. Open the pull request with the code change it belongs to. The reviewer checks the page
   against the screen.

## If something goes wrong

- **"Page not found"**: the address names no page. A file's number and `.md` are not part of
  the address, and a page inside a section needs the section in its address.
- **"Reported"**, when you did not mean to: nothing to undo. The IT Manager has a
  message saying the page needs a look; tell them it does not.
- **A number reads as an error rather than a value**: the token names a key that is unset or
  no longer exists. That is a defect in the page; report it.

## What happens next

A report writes an **Operator documentation flagged as out of date** entry to the audit trail
and notifies the IT Manager at once. There is no list of open reports yet: the
notification and the trail entry are the record, and the IT Manager fixes the page in a pull
request.
