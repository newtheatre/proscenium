The send log is where "did the reminder go out" is a lookup rather than an investigation. It is
at **Manage, Communications, Send log**, and at present the IT Manager is the only person who
opens it. Every message the theatre has tried to send is a line here with its outcome, the ones
that never reached the mail provider included, so a silence is always explained somewhere.

::callout{icon="i-lucide-info" color="info"}
The log is read only. Nothing on these screens changes an outcome or sends a message: a
further attempt happens on its own clock, and a message that has failed for good is sent again
from its source (the ticket re-issued, the reminder's cause put right), never from here.
::

## Reading the log

![The send log with the daily counts (1), the type search (2), the filters (3) and the log itself (4)](/images/docs/communications/send-log.png)

1. **Last 14 days** is a table of daily counts by type and outcome, so an outage at the
   provider shows as a dip or a run of failures rather than as nothing at all. Days are London
   days. When nothing was sent it says **"Nothing sent in this window."**
2. **Search** by message type, whole or in part: `shift.reminder`, or just `shift`.
3. **Filters** narrow by **Topic** (the five preference topics; a topic widens to every type
   under it), **Channel**, **Outcome** and **Sent** (a date range). The one sort is by when the
   message joined the queue, newest first. Active filters show as badges under the toolbar, each
   with its own clear, and **Clear all** empties them. Search, filters and page live in the
   address bar, so a filtered view can be bookmarked or sent to somebody.
4. **The log** shows one line per send: the **Recipient** (their name, linking to their
   history; or **No account** for a send to a configured address such as a report recipient),
   the **Type**, the **Channel**, the **Outcome**, when it was **Enqueued**, when it was **Sent**
   (or **Not sent**), and the provider's **Error** where there was one. The total reads
   "N sends" beneath, with paging when there is more than one page.

The subject line is stored on the row but this table does not show it; the name and the type
are usually enough, and the message body itself is never kept once a send has settled.

## Outcomes

The **Outcome** column and the outcome filter read the same words, and so does an export of
the log.

| Outcome | What it means | What to do |
| --- | --- | --- |
| Sent | The mail provider accepted the message. What happens after that is theirs. | Nothing. |
| Waiting to go | The message is claimed and about to go out. | Wait ten minutes; a line stuck here is worth reporting. |
| Failed, will try again | The provider refused it. The message is kept and will be tried again. | Nothing yet: see trying again, below. |
| Trying again | It is going out now. | Nothing. |
| Failed, no attempts left | Out of attempts, or it carried a file (a ticket, a calendar entry) that cannot be attached a second time. | Put it right at the source: re-issue the ticket, or tell the person yourself. |
| Held back by a preference | The recipient has that topic's email switched off. Their in-app entry was still written. | Nothing: it is their choice. An urgent message never lands here. |
| Skipped, no address to send to | It was never handed to the provider. The error column says why. | See the reasons below. |

The reasons a message is skipped, as the error column spells them:

- `unverified-address`: the account has never confirmed its address. Only verification, a
  sign-in link, a set-password invitation and a ticket to a guest may reach one.
- `anonymised`: the account was erased, before or while the message waited.
- `placeholder-address`: an address of the shape erasure or the old estate's merges leave
  behind (`deleted-...@`, `merged-...@`).
- `undeliverable-domain`: a reserved domain that can never receive mail, such as `.invalid`,
  `.test` or `example.com`.
- `no-address` or `no-account`: nothing to send to.
- `nothing to send again`, `unregistered-type`: a retry found no stored message, or a type
  retired between attempts.

## Retrying

Nothing on the screen retries a message. It happens on its own, every ten minutes:

1. A refused message waits {{ NOTIFICATION_RETRY_BACKOFF_MINUTES }} minutes for its first
   further attempt, then twice as long, then twice again.
2. Each attempt makes every check the first one made, so an address changed, a preference
   switched off or an account closed in between is honoured, and the line moves to whichever
   outcome that gives.
3. After {{ NOTIFICATION_MAX_ATTEMPTS }} attempts it reads **Failed, no attempts left** and the
   message is no longer kept. One carrying an attachment stops at its first refusal and says so
   in the error column: the file cannot be rebuilt afterwards.

Every attempt lands on the same line, so a count of lines is still a count of messages, and
**Failed, no attempts left** is the outcome to filter on when the question is "who did not get
theirs".

## One person's history

1. Choose a recipient's name in the log. Their history opens at
   `/comms/operations/accounts/<id>`, headed with their name.
2. It lists their sends with **Type**, **Channel**, **Outcome**, **Enqueued** and **Sent**, and
   nothing else. The screen says so at the top: **"Types, dates and outcomes only, never a
   message body."** A body might carry somebody else's data, so none is kept once a send has
   settled and none is shown here.
3. Narrow it with the type box (**"A message type, such as shift.reminder"**), which matches a
   whole type name. **Back to the send log** returns to the log.

Every view of a person's history is recorded in the audit trail with your name, theirs and
how many rows you saw. Open it to answer a question, not out of curiosity.

## What the log does not hold

- **In-app entries.** Those are written to the person's own recent messages and are never
  rows here.
- **A message held for a digest.** A plain announcement, a room request chase or a training
  nudge that was coalesced writes no row of its own; the digest that eventually carries it is
  the row (`digest.rooms`, `digest.announcements` and so on). The individual entries survive
  as long as that digest's row does.
- **Night reports.** A signed-off or auto-closed night report is distributed to its configured
  recipients on its own record, kept with the report, and is not tried again in the way
  described above.
- **Anything older than {{ NOTIFICATION_LOG_RETENTION_MONTHS }} months.** The log is thinned
  out each night past that. It answers a person asking what we hold about them, and so it is
  kept for a stated time rather than for ever.

## If something goes wrong

- **"Nothing sent yet."**: the log is empty. With filters set it reads **"Nothing matches
  that."** instead: clear one at a time.
- **"That account is no longer here."**: the history link points at an account that no longer exists. The
  log line stays; the person is gone.
- **"You do not have permission to do that"**: the log is not yours to read. Ask the IT
  Manager.
- **A run of failed lines with the same error**: the provider is the problem, not the messages.
  Watch the daily counts: once it recovers, the backlog goes out at up to a hundred lines every
  ten minutes.

## What happens next

Reading the log records nothing except a person's history, which is audited each time. Further
attempts and digests go out whether or not anybody is watching the screen.
