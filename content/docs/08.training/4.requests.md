A member who wants a module that has no session can request it from the catalogue. The
requests gather on the demand board at **Manage, Training, Requests**, so whoever can run a
session sees what is wanted. Anybody who can read the catalogue can open it; a department
lead sees requests for their own departments' modules only. The Theatre Manager declines one,
and so does a lead in their own department. How many requests are open,
counted the same way, shows beside **Requests** in the sidebar and on the console overview.

::callout{icon="i-lucide-info" color="info"}
A request is a demand signal, never a queue position. It confers no priority or place in any
session, and nothing here resolves on a timer: an ask nobody acts on keeps showing up, which
is the point of it.
::

## If something goes wrong

- **"That request has already been answered"**: somebody else got there first, or the member
  withdrew it. Reload the board.
- **"That request is no longer here."**: the request no longer exists. Reload.
- **"You do not have permission to do that"**: a lead is declining a request on a module
  outside their own departments.
- **"The board could not be read"**: the list failed to load, which is not the same as nothing
  being asked for. Reload, and if it keeps happening say so.

## Reading the board

![The demand board with a module's card (1), the count waiting (2) and a requester's Decline button (3)](/images/docs/training/requests.png)

1. Each card is one module, busiest first, with its id, title and department.
2. The badge counts how many people are **waiting** on it, and **Schedule a session** beside it
   opens [Sessions](/docs/training/sessions) with that module already chosen.
3. Under each module the requesters are listed with the note they wrote, and a **Decline**
   button beside each.

The board shows the busiest modules; schedule or decline some of these to see the rest. When
nothing is outstanding the screen says so.

## Scheduling a session instead

Most requests are answered by running the thing that was asked for. **Schedule a session** on a
module's card opens the scheduling form with that module chosen, so the rest of it is the date,
the times and the places. Once the session opens for sign-up, every outstanding request for that
module resolves on its own and each requester is emailed once. Nothing has to be answered by hand
afterwards.

## Declining a request

The one answer given by hand is a decline: a yes is a session, scheduled above. The requester is
shown what you write, so tell them where it stands rather than only that it is declined.

1. Press **Decline** beside the person.
2. Write **What to tell them**: "Not running this term, but it is on the list for next", for
   example. Nothing sends until you do, and a reply needs a few words at least.
3. Press **Decline and tell them**.

The request is marked declined and drops off the board. The person sees **Declined** and your
words against their request on their own training page.

## Scheduling instead

The better answer to a busy card is usually a session. When a session is scheduled and opened
for sign-up at once, every open request for a module it teaches is resolved and each requester
is emailed once, so they can sign up. See [Sessions](/docs/training/sessions).

## What happens next

A decline is in the audit trail, as **Training request declined**, with the actor and the module; the words you wrote are shown
to the requester and kept off the trail. A resolved request, whether declined or met by a
session, frees the member to ask again later.
