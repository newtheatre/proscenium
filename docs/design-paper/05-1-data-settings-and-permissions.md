# Data, settings and permissions

One D1 database per theatre, a schema owned module by module, and three registries (settings, permissions, data classes) that the build checks.

## Database

- **D1 only, through Drizzle.** No other database is supported, so no code carries branches for one.
- **Schema per module.** Each module owns its tables and prefixes their names.
- **Migrations are generated by the tool**, never written by hand, and bundled into the build.
- **Migrations run in the app.** First-run setup and an admin update card apply them and record each in a ledger table, as Mailflare does. No theatre runs a command line to upgrade.
- **A backup to R2 is taken before migrations run.** A failed migration leaves the previous version serving.
- **Atomic work is a batch.** D1 has no interactive transactions, so a unit of work is one batch of statements.
- **Contended claims are conditional writes** with the predicate on the statement, and a claim of several rows asserts that it got all of them.
- **Bound parameters are chunked**, and no query binds one parameter per row of a table it walks.
- **Capacity is a database constraint**, not a check in application code.

* **A new feature's data goes in new tables that read as empty until migrated**, so sign-in and the update card keep working on a database that is one release behind. This is the Mailflare port's practice.

## Records

- **Money is integer minor units with a currency code**, in an append-only ledger.
- **Append-only tables are enforced by triggers.** Corrections supersede; nothing is edited or deleted. A migration that would rebuild one is refused.
- **Times are stored in UTC** and shown in the theatre's time zone. The operating-day rollover hour is a setting. Date arithmetic goes through one calendar helper.
- **Identifiers are opaque and stable.** No table carries another system's ids.
- **Status changes write their audit entry in the same batch.**
- **Switching a module off never deletes data.** Tables stay; screens, routes and tasks stop.

## Data classes

Every column declares one class, and a check fails the build on an unclassified column.

| Class | Examples | On erasure |
| --- | --- | --- |
| Public | Production title, credited name with consent | Kept, or name replaced where consent is withdrawn |
| Internal | Stock level, shift template | Kept |
| Personal | Email, phone, booking name | Anonymised |
| Personal free text | Incident description, notes | Redacted or retained under a stated rule |
| Special category | Access needs, health details | Encrypted at rest in the application; deleted |

Erasure runs as one batch. The registry also generates the theatre's record of what personal data it holds, so the privacy documentation cannot drift from the schema.

## Settings

- **One registry.** Each setting has a key, a type, a default, validation, the ability needed to change it, and whether public pages may quote it.
- **Enforced at the write path.** A limit is checked where the data is written, not only in the form.
- **Quoted by token.** A content page writes a token and the live value appears. An unknown token fails the build.
- **No operational number is a constant.** A build check refuses one.
- **A change is audited.** Where a value could identify someone, the audit records a hash.
- **Presets.** A theatre type (student society, amateur company, small venue) sets sensible defaults in one step.

## Permissions

- **One registry of abilities**, declared by modules. Theatres map abilities to their own roles.
- **Three scopes:** the site, a module, or a single record.
- **Three sources of authority:** a granted role, a derived fact (tonight's shift, a production team place, a current training record), and ownership of the record.
- **Grants can expire** on a date the theatre sets, and nobody grants a role to themselves.
- **Checked on the server on every write**, with the same check driving what the interface shows.
- **An override is recorded when it acts**, not when it looks.

## Providers

Anything a theatre might do differently is an interface with more than one implementation.

| Interface | First implementations |
| --- | --- |
| Payments | In-person reader, online card, cash, none |
| Sign-in | Passkey, email link, Google, Microsoft |
| Outbound email | Cloudflare Email Sending |
| Membership verification | Staff confirmation, uploaded list |
| Public holidays | Government feeds by country |

NNT's reader-only payment and Workspace-only sign-in are two configurations of these, not special cases in code.
