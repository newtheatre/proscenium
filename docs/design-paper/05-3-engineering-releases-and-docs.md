# Engineering, releases and documentation

The same commands run on a contributor's machine and in CI, releases reach forks as a conflict-free merge, and documentation is generated wherever it can be.

## Tooling

- **bun only.** Never npm, pnpm or yarn.
- TypeScript in strict mode, one lint configuration for the whole repository.
- Generated files are never edited by hand, and each carries a marker saying so.
- Commands are repository-wide, and the foundations specification holds the current set (dev, check, test, test:browser, db:generate and verify, where check covers lint, types and the conformance checks). The first draft of this list read: `dev`, `preview`, `build`, `typecheck`, `lint`, `test`, `check`.

## Tests

- **Tests run on Linux, locally and in CI (decided: no Windows or macOS runs)**, against the real Workers runtime and a real local D1. This reverses Proscenium's CI-only rule and closes its gap of never exercising the D1 driver.
- **Three tiers:** unit, integration against D1, and end-to-end in a browser. A module ships with all three.
- **Named regression cases** for races: the last seat, the double refund, the shift claimed twice.
- **Upgrade tests.** Every release is tested as an upgrade from every earlier release, using a stored snapshot of each with data in place.
- **Module isolation tests.** Each module's suite is also run with the modules it only uses switched off.
- CI runs its gates in parallel and only what a change can reach. Nothing is skipped to get a green run.

## Environments

- **Local:** the dev server for interface work; the preview command for queues, cron, email and the Durable Object.
- **Preview:** pull-request previews are off by default, because a preview would share the production database; a theatre that wants them connects a second Worker with its own resources, so a branch never touches production data, as Mailflare does.
- **Production:** Cloudflare's own build service deploys the fork's main branch. Nobody deploys by hand.

## How work is done

- **Spec, failing test, implementation**, with documentation changed in the same pull request.
- **Few decision records.** A record is for a choice that is expensive to reverse. Screen-level rules live in the module's own docs.
- **A known-issues register** in the repository: a problem written down is one the next person does not rediscover.
- **Comments carry only what the code cannot say:** a constraint, a trap, a contract.
- **A `CLAUDE.md` at the root** holds the short list of rules an assistant or a newcomer must never break, as all four reference repositories do.
- British English in copy and documentation.

## Releases

- Semantic versions. A change to an extension point or a setting key is a breaking change.
- Release notes are written for a theatre's site owner, not for developers.
- **Stable and beta channels**, as Flytower has.
- The app shows the running version and whether a newer one exists.
- A scheduled pull request in each fork merges the newest release tag, with the release notes in its description.
- Rolling back is reverting the merge; migrations are written so the previous version still runs against the newer schema for one release.

## Documentation

Three audiences, kept apart.

| Audience | What they get | Where it lives |
| --- | --- | --- |
| People using the app | One page per screen, linked from that screen | In the module, shipped with the app |
| Site owner | Install, brand, configure, update, back up, troubleshoot | Platform documentation site |
| Contributors | Architecture, conventions, decisions, how to write a module | Platform repository |

- Screenshots are generated by the test suite, so they cannot drift. Both Proscenium and Flytower arrived at this.
- A check fails the build when a screen has no page or a documented setting no longer exists.
