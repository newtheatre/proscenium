# Lessons from Mailflare

Matt's Nuxt port keeps the original's server almost untouched and replaces everything around it, and the result is narrower, more consistent and easier to maintain than the React original. This comparison reads the port's `nuxt` branch against the original's `main` (the `upstream` branch, version 0.5.4 lineage) on 16 November 2026.

## The two side by side

|  | Original (hieunc229/mailflare) | Matt's port |
| --- | --- | --- |
| Framework | Next.js run through vinext, React 19 | Nuxt 4, Vue |
| Interface kit | Radix primitives with hand-built components, Hugeicons, React Query | Nuxt UI v4 throughout, bundled icons |
| Hosting | Cloudflare Workers or a Docker container on Node | Cloudflare Workers only |
| Database | D1, PostgreSQL, MySQL, libSQL from one schema; every change ships three migrations | D1 only; one migration, generated by Drizzle Kit 1.0 |
| Storage and mail | R2, Backblaze or S3; Cloudflare, Resend or Amazon SES | R2 and Cloudflare email only |
| Licensing | A paid licence gate on some features | No gate; everything on |
| Package manager | npm | bun |
| Cloudflare configuration | A hand-kept `wrangler.jsonc` | Declared in `nuxt.config.ts`, generated at build |
| Rendering | Server-rendered pages plus client | Client-rendered single-page app |
| Size | About 30,700 lines of interface code in 301 files, 53,900 of other TypeScript | About 37,500 lines in `app/` (299 Vue files), 44,000 in `server/` and `shared/` |
| Tests | 113 test files | 141, including Playwright suites for sign-in, passkeys, compose, admin and OIDC |
| CI | An update workflow only | Typecheck, lint, unit tests, build and end-to-end tests on every pull request |
| Updates for forks | An admin button dispatches a workflow that replaces the fork's whole tree with upstream's | A daily branch sync and a porting script, because the fork is a rewrite |

## How the port was done

- **The server was carried across, not rewritten.** 208 route handlers keep their Next.js shape and are mounted by one adapter, with a small stand-in for the parts of Next they use. Rewriting them would have bought nothing.
- **Route stubs and the migration bundle are generated**, and the generator never touches a file without its marker.
- **Work was split into numbered workstreams**, each owning named directories, with rules every thread followed and a status board in one file.
- **Every difference from the original is written down** in a deviations list, tagged by workstream or as a fork-only change.
- **API shapes were frozen** during the port, because mobile apps, JMAP and the public API depend on them.
- **Following upstream is planned for**, with a script that sorts each upstream change into carried mechanically, ported by hand, deleted on purpose or ignored.

## Where the port improves on the original

- **One of everything.** One host, one database, one storage, one mail provider. The original's instruction file opens with a rule to ship three migrations for every schema change; the port deletes that whole class of work.
- **A real component system.** Every page header is one component, and list, admin and settings pages render through one page layout. The original has these on mail pages only.
- **Confirmations are modals**, not browser `confirm()` prompts, in most places (three remain where the original's behaviour was kept).
- **Accessibility as configuration.** Badge colours are adjusted centrally to pass 4.5:1 contrast, form controls fill their fields by default, and an accessibility module is installed.
- **Security headers on every response** through route rules. They were missing from the first port and are now declared once.
- **Preview deployments with their own resources**, so a branch never touches production data.
- **Migrations that tolerate being unapplied.** New features put their data in new tables and treat a missing table as empty, so sign-in and the update card keep working before a migration runs.
- **New capability the original lacks:** an OpenID Connect provider, groups with nesting and delegated managers, shared inboxes and shared drives held by hidden accounts so they belong to nobody, a directory and org chart, all-day events, and better contacts.
- **Honest gaps are recorded**, such as the placeholder for assistant state and the three remaining browser prompts.

## What the port gave up

- Server rendering, which a signed-in app does not need but a public theatre site does.
- Docker and other databases, so it cannot run outside Cloudflare.
- Easy merges from upstream: a rewrite must be ported, not merged.

## What Proscenium takes from this

| Lesson | Where it lands in this paper |
| --- | --- |
| Cloudflare only, D1 only, one of everything | Part B, runtime |
| Bindings declared in the Nuxt configuration, generated Wrangler file | Part B, what Mailflare taught |
| A custom Worker entry for queue, email, cron and the Durable Object | Part B, what Mailflare taught |
| In-app migration runner with a ledger, from first-run setup and an update card | Data, settings and permissions |
| New features in new tables that read as empty until migrated | Data: now a rule there |
| One page component and one header for every screen | Security, privacy and interface |
| Preview deployments on preview-only resources | Engineering |
| Workstreams that own directories, rules for every thread, a status board | The next stage of this project |
| A deviations list | Becomes the fork's override list |
| Hidden accounts that own shared things, so they survive every person | Accounts: worth adopting for a production's or a department's shared records |
| Groups with nesting and delegated managers | Roles and permissions: a model for departments and production teams |
| An OpenID Connect provider | Lets Proscenium be the sign-in for a theatre's other tools, or accept Mailflare as its own |
| The original's update button for forks | Keep the one-click idea, but merge a release tag instead of replacing the tree, which owned paths make safe |

## The warning in it

Mailflare's fork is expensive to keep current because it changed files upstream owns. That is exactly what Proscenium's owned-path rule exists to prevent for theatres, and the original's replace-the-tree update shows the other failure: an update that is easy only because the fork may not customise anything.
